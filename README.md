# Спринт 1

Микрофронтенды и разбивка монолитной системы на микросервисы.

## Задание 1

Разделить проект Mesto на несколько микрофронтендов.

### Уровень 1. Проектирование.

Выбор фреймворка для создания микрофронтендов.

Между Webpack Module Federation и Single SPA нет принципиальных различий. Single SPA поддерживает независимость от фреймворков.
- Анализ кода исходного монолитного фронтенда показывает что он целиком написан на java script с использованием библиотеки react.
- Бекенд использует больший набор подключаемых библиотек, но задача стоит разделить только фронтенд.
- Во введении к практическому заданию спринта было наглядно показано как использовать Webpack Module Federation, а опыта роботы с Single SPA у команды (меня) нет.

Так как фронтенд-приложение довольно простое, использует одну библиотеку и имеется опыт работы с Webpack Module Federation, то выбор падает на него.


### Уровень 2. Планирование изменений.

Определить, какие компоненты в какой микрофронтенд пойдут.

Начнем с бизнес-логики. Сервис оперирует двумя понятиями:
- User (пользователь)
- Card (фотокарточка)

Это две основные сущности с которыми осуществляются какие-либо действия. Бекенд код правильно имеет отдельные модели для этих сущностей.
Как минимум нужно выделить два микрофронтенда: один для работы с фотокарточками и учетом лайков (лайки привязаны к ID карточки), второй для работы с пользователями.  
Сразу возникает мысль что возможно имеет смысл выделить сервис авторизации одельно. Это было бы логично если пользователей очень много и профиль пользователя будет богат разными настройками.
Тогда имеет смысл обрабатывать большое количество запросов авторизации и редактирование профиля пользователя отдельно, но это скорее всего больше проблемы бекенда.  
Предлагается создать пять микрофронтенд-приложений:
- microfrontend-host (маршрутизация)
- microfrontend-user (профиль пользователя)
- microfrontend-cards (редактирование фотокарточек)
- microfrontend-auth (логин и регистрация)
- microfrontend-layout (разметка страницы, хедер, футер)

Отдельный компонент layout появился в самом конце, когда пришло понимание что управлять размещением микрофронтендов будет неудобно, оставлять шапку и футер в host не хочется,
его роль не рисовать, а соединять других. Можно было вынести их в auth, но пришла идея сделать отдельно. Google подтвердил что так делают.

API методы microfrontend-auth:
- register
- login
- signout
- checkToken

Компоненты microfrontend-auth:
- Register
- Login
- InfoTooltip
- ProtectedRoute (переключение)

API методы microfrontend-user:
- getUserInfo
- setUserInfo
- setUserAvatar

Компоненты microfrontend-user:
- EditAvatarPopup
- EditProfilePopup

API методы microfrontend-cards:
- getCardList
- addCard
- removeCard
- changeLikeCardStatus

Компоненты microfrontend-cards:
- ImagePopup
- AddPlacePopup
- Card

Компоненты microfrontend-layout:
- Header (функция signout перенесена в auth)
- Footer
- Main

Все микрофронтенды будут работать через свой уникальный порт.  
Компоненты всех микрофронтендов, подключаемых для использования в host, будут указаны в exposes секции своих webpack.config.js.  
В remotes секции webpack.config.js микрофронтенда host будут указаны компоненты подключаемых микрофронтендов.  
Маршрутизация будет настроена в App.jsx микрофронтенда host.  
Дерево состояний будет выглядеть так:
- Пользователь не залогинен
- Пользователь залогинен

Если пользователь не залогинен, то будет доступна только функция переключения между состояниями:
- Signup (регистрация)
- Login (вход)

Если пользователь не залогинен, то будут доступны следующие компоненты:
- Main/Header/Footer (layout, показываются всегда)
- Login (auth)
- Signup (auth)
- Переключение Login/Signup (auth)

Если пользователь залогинен, то будет доступны функции выхода, управления профилем и управления фотокарточками:
- Signout (выход)
- Edit avatar/user info
- Add/delete/show card
- Like/dislike card

Если пользователь залогинен, то будут доступны следующие компоненты:
- Main/Header/Footer (layout, показываются всегда)
- Signout (auth)
- EditAvatarPopup (user)
- EditProfilePopup (user)
- ImagePopup (cards)
- AddPlacePopup (cards)
- Card (cards)


## Задание 2

Декомпозировать веб-приложения на Django на микросервисы.

### Уровень 1. Разделить монолит на компоненты.

[Предлагаемая схема решения в Google Drive](https://drive.google.com/file/d/1zsTp0fBTIXbXB94AlhkoIn_OKAmJZKAq/view?usp=sharing)  

Разберем основные бизнес-процессы и их особенности.  
1. Регистрация и авторизация пользователей, как покупателей, так и продавцов.  
Пользователь имеет ID, роль, данные и права.  
Происходит верификация пользователя и допуск к действиям на платформе.  
2. Профиль пользователя.  
Это данные о пользователе, связанные с ним транзакции, товары, услуги.  
Здесь пользователь может оставлять данные о себе и получать данные связанные со своим ID, например историю покупок.  
Предлагается иметь свою базу данных с данными пользователей. К ней могут делать запросы другие службы.  
Есть связь с ID заказов, торговых площадок и заявок на открытие аукционов (для продавцов)  
3. Отдел поддержки пользователей.  
Должна быть форма связи с поддержкой.  
Службе поддержки передаются ID пользователя, ID транзакций и ID заказов. Формируется ID тикета.  
Можно вести свою отдельную базу данных тикетов поддержки.  
4. Сервис поиска товаров и услуг.  
Это каталог, список карточек товаров и услуг, система поиска и фильтрации.  
Здесь же может быть встроены как прямая покупка, так и аукцион.  
Можно с переключением режимов, можно одновременно.  
Здесь нужна база данных ID товаров, ID услуг и их данных.  
5. Сервис корзины.  
По сути это коллекция отложенных товаров до оплаты.  
Здесь могут применяться скидки, купоны, бандлы.  
Отсюда инициируются запросы на оплату.  
6. Сервис оплаты.  
Здесь инкапсулировано взаимодействие со внешними сервисами оплаты и банками.  
Формируется ID транзакции. Есть база данных транзакций и их статусов и связь с ID заказа.  
7. Сервис отслеживания заказов.  
Это коллекция уже обработанных заказов. Отсюда можно отменять оплату, отменять заказ.  
Можно отслеживать процесс обработки, резервирования на складе, оплаты и отправки заказа.  
8. Сервис управления листингами и аналитика для продавцов.  
Редактирование карточек товаров, управление аукционами.  
Получение статистики и аналитики.
